# Mobile Backend Readiness Assessment

Assessment date: 2026-10-15

Scope: static, read-only assessment of the MyCareSight Next.js backend for a separate React Native / Expo caregiver application. No application code, database schema, authentication configuration, environment variable, dependency, or remote resource was changed. Local `.env.local` values were intentionally not inspected or reproduced. Azure and database statements below distinguish repository evidence from live-resource verification.

## Executive assessment

The existing Next.js application is the correct backend gateway for the mobile application. It already has a Neon-backed identity model, random opaque sessions, active-membership checks, tenant-aware PostgreSQL execution, caregiver visit workflows, RLS defenses, audit records, Azure storage boundaries, and shared Zod validation. These controls should be extended rather than reimplemented in the mobile repository.

The backend is not ready to accept a mobile client yet. There is no browser-to-mobile authorization-code flow, no device-scoped bearer session, no MFA implementation, no `/api/mobile/v1` contract, no replay-safe offline EVV ingestion, no push-device registry, and no OpenAPI document. Most caregiver services obtain the actor from the Auth.js browser cookie, so the existing server actions must not be exposed directly as mobile APIs.

A secure browser-to-mobile exchange is architecturally feasible with the existing identity and session foundation. It requires a short-lived, single-use authorization code bound to PKCE, followed by issuance of a separately identifiable opaque mobile session. The API must resolve a bearer token to a current active user, active agency membership, and active caregiver record on every protected request, then enter the existing database actor context.

#### Mobile-auth conclusion

The existing system can be the identity authority for mobile, but it cannot currently perform the approved flow. The existing browser cookie is appropriate for the web application and must not be copied into native storage or treated as a mobile bearer token.

The missing pieces are:

1. A mobile login transaction endpoint that creates a bounded `state`, PKCE challenge, nonce, app/environment identifier, and allowlisted callback.
2. A browser completion endpoint that requires the existing Auth.js session and issues a short-lived, single-use, hashed authorization code.
3. A code-exchange endpoint that verifies state, PKCE, expiry, one-time use, active identity/membership, and app environment before issuing an opaque device session.
4. Mobile session metadata and policy: session type, device installation identifier, issued/last-seen/absolute expiry, revocation reason, and optional device label. Raw tokens must remain client-only and be stored in the platform secure store.
5. A bearer-token actor resolver for `/api/mobile/v1` that reloads current identity, exact active membership, active caregiver status, and feature capability before entering `withUserContext`/`withActorContext`.
6. Current-device logout, logout-all, administrative revocation, password/security-event revocation, device list, and rate limits. Existing database triggers should revoke mobile sessions as well.
7. An MFA decision and implementation. The mobile design cannot reuse an MFA policy that does not yet exist.

### 1.2 Tenant and database authorization

The server-only PostgreSQL client uses TLS, the Neon pooler, and a restricted runtime role. `withUserContext` starts a transaction and sets `app.current_user_id`, `app.current_user_role`, and `app.current_agency_id` with transaction-local scope; `withActorContext` prevents one verified actor from being replaced inside an existing transaction. This is the right foundation for bearer-authenticated mobile requests. See [`src/db/index.ts:1`](../src/db/index.ts#L1), [`src/db/index.ts:59`](../src/db/index.ts#L59), and [`src/db/index.ts:83`](../src/db/index.ts#L83).

Authorization is strong in the newer domain repositories but is not fully centralized. For example, caregiver visit execution reloads the active profile, exact active `staff_member` membership, active caregiver record, and `care_operations` capability before work begins. Other utilities and server actions call `getSession()` directly, and some historical query functions assume a verified caller. The mobile layer therefore needs a single request-actor boundary and repository methods that accept that verified actor; it must not pass client-supplied user, caregiver, agency, patient, or sender IDs as authority. See [`src/lib/repositories/caregiver-visit-execution.ts:45`](../src/lib/repositories/caregiver-visit-execution.ts#L45), [`src/lib/permissions.ts:15`](../src/lib/permissions.ts#L15), and [`src/db/index.ts:59`](../src/db/index.ts#L59).

Caregiver EVV records also have RLS defense in depth. Database policies require the current user to be the active caregiver assigned to the same-agency visit, and column grants constrain caregiver updates. See [`scripts/migrations/010-caregiver-visit-execution-access.sql:34`](../scripts/migrations/010-caregiver-visit-execution-access.sql#L34), [`scripts/migrations/010-caregiver-visit-execution-access.sql:52`](../scripts/migrations/010-caregiver-visit-execution-access.sql#L52), and [`scripts/migrations/010-caregiver-visit-execution-access.sql:88`](../scripts/migrations/010-caregiver-visit-execution-access.sql#L88).

## 4. API readiness

### Current conventions

- Only Auth.js, storage/document, contact/email, template conversion, and a versioned website-lead integration exist under `src/app/api`; no `/api/mobile` route exists.
- Protected user APIs generally call `getSession()` and therefore depend on the Auth.js cookie. The website-lead integration accepts a bearer credential, but that credential represents an agency integration, not a human/device session. Compare [`src/app/api/storage/signed-url/route.ts:5`](../src/app/api/storage/signed-url/route.ts#L5) with [`src/app/api/integrations/v1/leads/route.ts:22`](../src/app/api/integrations/v1/leads/route.ts#L22).
- Authorization is centralized at the session and PostgreSQL actor-context layers, but domain repositories are mixed: newer ones perform strong actor checks, while historical query functions require a trusted wrapper.
- Agency isolation is enforced by current-identity checks, exact active membership, explicit `agency_id` predicates, transaction-local actor variables, restricted grants, and RLS on protected tables. Mobile routes must preserve all layers.
- Error formats are inconsistent: the lead API uses stable machine codes, storage routes return English `{ error }` strings, and server actions return a mixture of `{ success, error, fieldErrors }`, `{ ok, error }`, and repository result shapes. Mobile needs one versioned error contract with a non-PHI correlation ID.
- The website-lead API has full request idempotency backed by key/body hashes. Current caregiver mutations do not have a general client-event idempotency facility. Clock retries happen to be state tolerant, shift interest reuses an existing pending request, and notes/tasks are effectively last-write-wins. See [`src/app/api/integrations/v1/leads/route.ts:46`](../src/app/api/integrations/v1/leads/route.ts#L46), [`src/lib/repositories/lead-integrations.ts:164`](../src/lib/repositories/lead-integrations.ts#L164), and [`src/lib/repositories/visit-shift-offers.ts:311`](../src/lib/repositories/visit-shift-offers.ts#L311).
- No OpenAPI/Swagger document, generated client types, or contract-generation dependency was found.

### Required mobile API conventions

All `/api/mobile/v1` routes should:

1. Require `Authorization: Bearer <opaque-device-token>` and reject cookie fallback to prevent confused-authentication behavior.
2. Resolve the bearer token server-side, reload active identity/membership/caregiver state, enforce capability and tenant scope, then set the PostgreSQL actor context.
3. Accept no authoritative user, caregiver, or agency ID from the client.
4. Set `Cache-Control: no-store`; define bounded body/file sizes and strict content types.
5. Use shared Zod schemas and a stable error body such as `{ error: { code, message, fields?, requestId } }` without internal/provider details or PHI.
6. Require a stable client event/idempotency ID for every replayable mutation and store a request hash to reject key reuse with changed content.
7. Return canonical server state and a revision/version after every write so the client can reconcile offline changes.
8. Generate OpenAPI from the same schemas or validate a maintained OpenAPI contract against them in CI.

The mobile project should use separate application identifiers and redirect origins for development/UAT and production. Each build must receive only its public API origin and public app-link configuration; database, Blob, Key Vault, email, and Auth.js secrets remain exclusively in the Next.js/Azure environment.

## 6. Missing capabilities and security risks

### Blocking gaps

1. **No mobile authorization-code flow or bearer actor.** Calling the Credentials endpoint from the native app or copying an Auth.js cookie would bypass the approved system-browser exchange and leave no device-scoped revocation model.
2. **No MFA implementation.** Mobile cannot inherit MFA enrollment or proof until WebAuthn/passkey/TOTP policy and recovery behavior are implemented for the shared identity.
3. **No offline EVV ingestion model.** Current clock methods use server receipt time and optional coordinates. Offline EVV needs immutable captured-at and received-at timestamps, accuracy/provider/permission state, visit and device binding, event ordering, geofence result/exception, and replay-safe event IDs. A device clock must be treated as evidence, not authoritative billing time.
4. **No general mobile idempotency or conflict contract.** Task, note, clock, and shift mutations need unique client-event IDs, request hashes, stored outcomes, and deterministic duplicate/conflict behavior.
5. **No push registration/delivery boundary.** In-app notifications exist, but native push lifecycle does not.
6. **No OpenAPI/mobile contract.** Without a checked contract, the backend and separate Expo repository can drift silently.
7. **Caregiver messaging is not ready.** Current message queries are application-oriented and some accept a caller-supplied `sender_id`; they must not be reused as mobile write endpoints without a participant-scoped repository.

### Existing risks to remediate before reuse

- The assessment found that open-visit request notes and adjacent assignment-decline reasons could be copied into `audit_log.details`. The follow-up repair keeps the authorized text in the business workflow while limiting audit details to identifiers plus text-presence and length metadata. Focused regression coverage prevents either free-text value from entering the audit call. See [`src/app/actions/schedule-assignment-requests.ts:51`](../src/app/actions/schedule-assignment-requests.ts#L51) and [`src/_tests_/schedule-assignment-audit.test.ts:44`](../src/_tests_/schedule-assignment-audit.test.ts#L44).
- Active visit task DTOs omit task instructions even though the task table can contain them. Adding them to mobile requires a deliberate caregiver-safe disclosure rule, not a broad patient/care-plan response. See [`src/lib/caregiver-visit-execution.ts:155`](../src/lib/caregiver-visit-execution.ts#L155) and [`src/lib/caregiver-visit-execution.ts:321`](../src/lib/caregiver-visit-execution.ts#L321).
- Storage authorization and notifications are tied to `getSession()`. Adding a second parallel implementation would create policy drift; both need actor-injected service functions shared by web and mobile adapters. See [`src/lib/storage/authorization.ts:43`](../src/lib/storage/authorization.ts#L43) and [`src/lib/repositories/notification-lifecycle.ts:24`](../src/lib/repositories/notification-lifecycle.ts#L24).
- Error handling is inconsistent, and at least one unrelated API returns provider exception text. Mobile routes need sanitized errors and must not copy that pattern. See [`src/app/api/send-email-notification/route.ts:41`](../src/app/api/send-email-notification/route.ts#L41).
- Remote revocation cannot erase PHI from an offline device immediately. The mobile design needs encrypted native storage, minimal cached fields, short offline retention, lockout on session expiry where feasible, server-side revocation, and local purge on logout/account removal. This remains a mobile-client and policy requirement even after backend revocation exists.
- UAT is explicitly synthetic/non-PHI and production still uses a separate architecture. Mobile development must not introduce real caregiver/client/visit information into UAT or assume UAT infrastructure settings are production-ready.

## 7. Recommended implementation sequence

1. **Approve identity and session policy.** Decide MFA timing, system-browser flow, PKCE/app-link choices, mobile session idle/absolute lifetimes, device limits, logout-all behavior, and development/UAT application identifiers.
2. **Create and test the mobile auth foundation.** Add one-time authorization-code state, device-scoped opaque sessions, hashed-token storage, bearer actor resolution, rate limits, revocation triggers, logout/current-device/all-device endpoints, and identifier-only auth audits. Keep Auth.js as the browser authentication authority.
3. **Define the API standard and OpenAPI skeleton.** Establish `/api/mobile/v1`, response/error envelopes, pagination, idempotency headers or event IDs, request IDs, `no-store`, versioning/deprecation rules, and schema-to-contract generation. Generate the Expo client types from the reviewed contract.
4. **Refactor shared domain services.** Make caregiver visit reads/execution, shift responses, notifications, and storage authorization accept a verified actor. Keep thin web server-action adapters and add thin mobile route adapters around the same services.
5. **Ship read-only mobile endpoints first.** Start with session/profile, assigned visit list, visit detail/task snapshot, open offers, and notification inbox. Validate minimum-necessary disclosure, tenant isolation, revocation, and audit behavior before writes.
6. **Implement online EVV writes.** Add clock-in/out and task/note mutations with idempotency, event revisions, geofence policy/exception handling, authoritative server decisions, and audit controls. Do not add offline queuing until the online event contract is stable.
7. **Add offline EVV synchronization.** Introduce an immutable event ledger and bounded batch endpoint with per-event outcomes, request hashes, device/session binding, captured/received times, ordering/conflict rules, and retry-safe processing. Exercise airplane-mode, clock drift, duplicate, tamper, expired-session, reassignment, and revoked-device cases.
8. **Add push registration and delivery.** Create an application-owned push provider interface, per-installation token records, environment/app binding, preferences, token rotation/deletion, delivery outcomes, and PHI-minimized payload rules. Push content should tell the app to fetch authorized data rather than include client/visit PHI.
9. **Add caregiver messaging and uploads only after their domain models are approved.** Build visit/agency participant authorization for messaging and visit-document metadata/quarantine for uploads. These should not block the initial schedule and EVV MVP unless explicitly included.
10. **Run environment acceptance gates.** Verify exact origins, app links, managed identities, Key Vault/Blob roles, Neon restricted roles/RLS, telemetry redaction, synthetic UAT end-to-end tests, revocation, backup/recovery, and production migration readiness separately. Production configuration remains out of scope until authorized.

## 8. Decisions requiring approval

Implementation should wait for approval on these points:

1. **MFA scope:** implement shared MFA before caregiver mobile pilot, or explicitly limit the synthetic UAT pilot while MFA is completed before any external user/PHI use. The safer recommendation is shared MFA before external access.
2. **Mobile session policy:** recommended 15-minute idle-sensitive access checks with server-side last-seen tracking, a 12-hour maximum authenticated work period, explicit device revocation, and reauthentication for sensitive account actions. Exact idle/absolute lifetimes need operational approval.
3. **Session data model:** recommended additive extension of the existing `auth_sessions` revocation foundation for session type/device metadata, plus a separate one-time authorization-code table. This preserves the existing identity-change revocation behavior without building a second auth system.
4. **App-link model:** approve separate development/UAT and production bundle identifiers, universal/app links, and allowlisted callback origins. Custom schemes may be a fallback, not the only production callback mechanism.
5. **EVV rules:** define geofence radius, early/late windows, location-denied behavior, manual exception and supervisor review, offline grace period, device-clock tolerance, reassignment conflicts, and the time used for payroll/billing decisions.
6. **Open-shift MVP:** choose targeted/all-eligible offers, the broad PHI-minimized same-agency open list, or both. Current backend behavior supports both concepts but they have different notification and operational semantics.
7. **Caregiver-safe visit data:** approve the exact fields available before arrival, after assignment, during a visit, and after completion, including address, instructions, diagnoses/alerts, contacts, documents, and retention on device.
8. **Push provider:** approve Expo Push Service versus direct APNs/FCM after BAA/data-flow review. Payloads should remain PHI-minimized regardless of provider.
9. **MVP boundaries:** recommended initial scope is authentication, assigned/open visits, visit detail/tasks, online clock-in/out, notes, shift responses, and notifications. Messaging, photos/documents, availability editing, and advanced offline conflict UI should follow after the core EVV contract unless business operations require them at launch.
10. **Production timing:** approve mobile production work only when the separate production backend migration and production Azure/Neon/Blob/Key Vault controls are in scope. No production base URL can be safely assigned from this repository today.

## Final readiness determination

**Foundation readiness: conditional yes.** The current identity, membership, tenant context, RLS, caregiver repositories, and infrastructure boundaries are suitable foundations.

**Mobile API readiness: no, implementation required.** The first approved engineering slice should be mobile authentication/session design plus the `/api/mobile/v1` contract and read-only caregiver endpoints. Offline EVV, push, messaging, and uploads should build on that verified foundation in the sequence above.
