## Remaining milestones before data migration

1. **Application hosting:** Verify App Service identity, VNet outbound integration, private Key Vault/Blob DNS and access, production-only app settings, HTTPS/custom domain, health endpoint, and safe network exposure. Verify staging-specific data services and settings before any synthetic test or swap; the staging slot must not inherit future production PHI access.
2. **Recovery and monitoring:** Verify App Service, Neon, Key Vault, and Blob restore procedures with synthetic data; define recovery time/point objectives. Verify Application Insights/Log Analytics sampling, PHI redaction, retention, alert delivery, and operator access. App Service backup does not replace Neon or Blob recovery.
3. **Release path and independent review:** Choose the canonical GitHub repository and exact release SHA; protect the release path. Identify a second trusted reviewer with repository access, confirm that the repository plan supports required reviewers for its visibility, then configure `production-staging` with that reviewer, `Prevent self-review`, and administrator bypass disabled. Verify with a synthetic deployment that the job waits for approval. Configure a separate GitHub `production` environment with available reviewer controls, environment-scoped values, and a production-only Azure OIDC identity restricted to the target app/slot. Build and validate from the exact SHA, deploy to staging, test, then require a manual release decision. Retire local file copying as the release method. A manual database import is outside GitHub's deployment approval gate and requires a separately recorded, independent sign-off on the migration runbook before data movement.
4. **Migration control without data movement:** Prepare an ordered, immutable migration manifest and target-identity preflight. Reconcile the live Supabase source and Neon target schema metadata and classify remaining index, constraint, grant, RLS, trigger, function, and storage-contract differences before any import. Keep source data, row contents, and credentials out of the repository and CI.
5. **Synthetic acceptance:** With no production PHI, verify startup, health, login/recovery, tenant denial, role access, private document upload/download, email, Turnstile, background jobs, audit events, and alerting. Record the deployed SHA, configuration version, test evidence, and rollback path.
6. **Compliance sign-off:** Confirm provider BAAs/eligibility, production RBAC and break-glass ownership, key recovery, retention, incident response, and named go/no-go authority. No external users or PHI may enter the new target before these gates are accepted.

Current implementation gap: the app returns direct Blob SAS download URLs to browsers. Disabling the storage account's public endpoint would block those downloads for users outside the VNet. Before PHI or external users enter the new target, choose and test either tightly controlled direct SAS access with a public network endpoint or an application-mediated download path with private-only storage. The staging account's current public endpoint is for synthetic acceptance and is not evidence that the future production storage exposure is approved.

The prepared manual staging workflow requires GitHub environment variables `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_SITE_URL`, `STAGING_AUTH_URL`, and `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, plus environment secrets `STAGING_AUTH_SECRET` and `STAGING_DATABASE_URL`. The `STAGING_AUTH_URL` variable and two secrets must match the isolated staging slot's `AUTH_URL`, `AUTH_SECRET`, and Neon `DATABASE_URL`; do not use production values or source data. The workflow runs only when manually dispatched from `main` in `homesight-app/MyCareSight-Dev`, checks out that exact SHA, validates/builds, and names the `staging` slot explicitly. The environment's deployment-branch rule reportedly allows only `main`; an independent required reviewer is not configured. Azure's Website Contributor grant at the parent App Service also permits management of the default production slot; the workflow target and GitHub controls reduce this risk but do not create a slot-only Azure permission. Do not run the workflow until the build values and protected environment are verified; the reported SCM setting permits runner reachability but is not evidence of a successful deployment or an approved PHI-ready network boundary.

The synthetic authentication gate is accepted on operator-reported evidence: login, reset, bootstrap, sign-out revocation, protected-route redirect, and staging database target were checked without sharing identifiers or credentials. A dedicated `/api/health` path is prepared locally: it checks database reachability through the server repository boundary, returns only 200 or 503 with no body, and disables caching. It has not been deployed or verified on staging. After release to staging, verify it returns 200 and then configure the staging slot's Health check path. Continue to synthetic storage, Turnstile, alert, and recovery acceptance. Review whether a separate append-only sign-out event is required before PHI-bearing use; the current session row records revocation reason but the sign-out path writes no separate audit event. Do not copy a UAT identity or credential. This bootstrap is not a substitute for the independent-review and production identity-migration decisions above.
